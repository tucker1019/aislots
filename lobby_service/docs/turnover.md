# 取款流水要求

金额均为整数分。用户的待完成要求按入账和有效投注的实际处理顺序累计：

- 新增加币：`remaining += creditAmount × multiplier`。
- 可信有效投注：`remaining = max(0, remaining - validBet)`。
- 派彩和取款退回本金固定不增加要求；其他来源配置 0 时不增加要求。
- 超额投注不预存，不能抵扣以后领取的奖励。免费局和消除没有新付费投注，不额外抵扣。

## 配置

默认 `etc/turnover.json`；`LOBBY_TURNOVER_CONFIG` 可指定路径，重启加载。每种来源独立配置非负整数倍数（0–1000000），不接受负数、小数、未知或缺失来源。当前所有非豁免加币默认 1 倍。

| source | 加币类型 | 默认倍数 |
| --- | --- | --- |
| rch_001 | 充值本金 | 1 |
| rch_002 | 充值赠送 | 1 |
| act_001 | 签到 | 1 |
| act_002 / act_003 / act_004 | 日 / 周 / 月反水 | 各 1 |
| act_005 | 亏损返还 | 1 |
| vip_001 / vip_002 / vip_003 | VIP 升级 / 周 / 月礼金 | 各 1 |
| act_006 | 新手充值奖励 | 1 |
| act_007 | 邀请奖励 | 1 |
| agt_001 | 代理佣金 | 1 |
| wdr_003 | 取款通过赠送 | 1 |
| game_002 | 游戏派彩 | 固定 0 |
| wdr_002 | 取款退回本金 | 固定 0 |

来源 ID 仍只在 `script/coin_sources.py` 注册。新增加币来源须同时加入流水配置校验和配置文件；未配置的新来源入账会失败并回滚，不会默认为免流水。原始加币明细的金额、倍数、配置版本及新增要求永久保存；改配置不改变旧要求。

例如本金 1000×1、充值赠送 30×3，新增要求1090；有效投注30后剩1060，再领取反水100×2，剩余1260。

## 数据和事务

迁移 `019_turnover.sql` 新增：

- `lobby_turnover_activation`：首次启用时间，重启不移动。
- `lobby_turnover_rules`：当前入账规则；启动时在单个事务中更新。
- `lobby_turnover_balances`：每位用户的剩余要求。
- `lobby_turnover_entries`：加币/有效投注审计，包含来源、关联资金流水或业务事件、增加、抵扣及变更前后数值。

资金流水的新增正向入账由数据库触发器同步增加要求；可信 `game_bet` 事件插入时同步抵扣，优先使用 `valid_bet_amount`，历史字段缺省时使用实际投注 `amount`。其他活动类型不抵扣。两者与原有钱包事务一起提交或回滚，使用同一用户钱包行锁；订单和事件幂等重试不产生新明细，不重复累计。

迁移不扫描或回填历史资金流水、历史投注。启用前发生的记录即使后来导入也不参与；启用后新领取的奖励即使所属活动周期较早，仍按领取入账时的规则增加要求。迁移重复执行、重启和规则调整均不重置剩余要求。历史钱包余额可继续使用，不追溯施加要求。

## 查询和取款

`POST /api/user/withdrawal/turnover`，请求当前登录 `uid/sid`，响应：

```json
{"code":"OK","data":{"remaining":126000,"canWithdraw":false}}
```

`canWithdraw` 只表示流水条件已满足，其他条件（余额、档位、绑定账号）仍单独校验。查询数据只供显示；创建取款订单时，在钱包锁内再次检查。剩余大于 0 返回 HTTP400、code10010025，不创建订单或扣钱。

同一请求号已创建的订单优先返回原回执，不因之后新增流水要求而阻断确认。已创建的待审核订单也不会被后来的奖励取消；新增要求只限制后续新申请。退回本金不增加要求，成功赠送按 wdr_003 配置增加。

客户端显示待完成有效流水，不满足时禁用新申请；查询失败不能当0，不得自动重新提交取款。未确认申请沿用原请求号确认结果。窗口重新聚焦可重新查询，没有定时轮询流水要求。

## 验证

数据库用独立 schema 覆盖全来源默认值、示例计算、0倍、豁免、历史记录、重启不重算、快照、并发加币/投注、重复事件、回滚、取款拒绝及已有订单重试。前端使用模拟接口，测试过程中不发起真实取款或领取。
