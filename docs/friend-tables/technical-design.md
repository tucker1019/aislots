# 好友桌：技术方案

状态：设计草案，未实施。下列接口、表名及事件均为建议，不代表已存在。前置阅读：[需求](requirements.md)、[工作流](workflows.md)。

## 结论与现有链路差异

需要长连接，建议 WebSocket 负责实时展示；比赛推进必须由持久化服务端任务负责。断线、浏览器节流、页面关闭以及 WebSocket 故障不能使比赛停在一半。

沿用大厅作为唯一真实钱包，游戏服务负责 RNG、盘面和完整付费链。新增好友桌协调、预付本金与专用结算场景，不能直接把普通 Spin 接口包装成新页面。

| 现有依据 | 好友桌必须新增的能力 |
| --- | --- |
| [大厅游戏接入说明](../../lobby_service/docs/game-integration.md)：两服务独立数据库，逐帧钱包回调 | 入桌一次扣款、预付消费、可信房间上下文、跨库幂等恢复 |
| [游戏客户端接口](../../slots_service/docs/client-api.md)：一次请求可能只取下一帧 | 以完整付费链计N，保留消除及免费游戏派彩，不把帧数当局数 |
| `GameModel.Settle` 当前写普通投注／派彩并调用 `recordActivity` | 在入账前按可信场景分流，好友桌走独立资金、事实和报表 |
| `recordActivity` 当前区分真实／体验账号并更新VIP等 | 真实好友桌仍为真实账号；不得伪装体验账号绕过活动 |
| `personal_report_model.go` 按普通钱包来源及活动汇总 | 独立汇总预付消费与好友桌来源，普通报表排除好友桌 |
| `internal/application/play/auto_round.go` 已有持久自动局任务 | 可借鉴任务机制，但现有自动局没有完整好友桌预付／场景隔离能力，不能直接复用上线 |
| [提现流水迁移](../../lobby_service/deploy/migration/019_turnover.sql) 的入账来源规则与投注触发器 | 新来源须先有明确规则；活动排除不等于提现流水已处理 |

实现前还需对选定首发游戏核实开放局、跨局状态和自动局锁；不能凭旧架构说明假定所有游戏共用一把玩家锁。

## 服务职责

| 部件 | 职责 |
| --- | --- |
| 大厅好友桌模块 | 参数校验、入桌／退出／开始、状态机、名单和规则快照、调度、成绩与奖池结算 |
| 大厅钱包与分账 | 余额、一次扣款、本金／奖池账户、退款、派彩、资金流水和幂等收据 |
| 游戏服务 | 可信上下文校验、合法实际Bet、普通RNG与派彩、持久开奖结果、逐帧与付费链完成事实 |
| 持久任务执行器 | 按桌／玩家推进、租约与栅栏、超时恢复和重试；不依赖页面在线 |
| Outbox与事件投递 | 本地事务内存事件，至少一次投递，消费者幂等处理 |
| WebSocket网关 | 身份与房间成员授权、已公开帧推送、序号补发、心跳与限流 |
| 报表与活动 | 好友桌独立读模型；普通活动默认排除；未来专属奖励独立消费完成事实 |

首版建议维持现有服务边界，在大厅内新增业务模块与worker，不先拆出额外微服务。无需先做聊天或完整好友关系系统。

## 可信执行上下文和游戏适配

开桌校验 B 是游戏实际合法投注：普通输入金额还可能乘线数、Bet档位等。服务端依据固定游戏配置计算并返回 B，不能信任前端自己计算的 `bet × N`。金额乘法检查溢出，N／B／S使用服务端允许范围。

房间创建时绑定游戏构建、数学配置版本、实际Bet、N、S、规则版本、活动时区和可选奖励版本。后续新配置只作用于新桌；进行中的桌必须继续使用可执行的旧版本，不能仅存版本号却已删除对应配置。

内部授权绑定 `scene=friend_table、roomId、memberId、uid、gameId、paidSpinIndex、requestId`。外部客户端不得通过传 scene 跳过钱包扣款。该上下文须贯穿启动票据、局记录、待结算计划、settle、完成事件和账本，不能只留在页面或HTTP参数里。

游戏状态应按房间成员隔离，普通会话不能读取或推进该桌的帧。首版建议参加一桌期间禁止普通Spin；有未完成普通付费链时先完成再允许入桌。对于持久收集、累积进度、大奖资格等特征，必须逐游戏决定如何延续和隔离，不能重置有价值状态或通过重复开桌获得有利初始状态。不能绕过原游戏数学规则。

## 资金模型与不变量

所有金额使用现有最小货币单位整数。内部使用可审计分账／复式记账等价结构，钱包日志与业务分账在同一大厅数据库事务提交。

- 进入：锁房间与账户，校验版本、席位、余额、参赛限制；钱包减 `S+B×N`，本金账户加 `B×N`，奖池账户加S，记录正式成员和Outbox。任何一步失败全部回滚。
- 付费局：为唯一局序号消费一次B；免费／消除帧消费0。本桌预付本金不足属于异常，暂停，禁止补扣可用钱包。
- 派彩：游戏确认的每帧 credit 只入钱包一次，写好友桌游戏派彩来源；总成绩只汇总这些唯一已确认派彩。
- 正常完结：每人恰好N条完整付费链，未用本金0；先校验游戏侧无待结算帧，再一次事务记录排名、扣清奖池、向赢家／平局退还入账、写完成事件。
- 开始前取消：同事务锁定未开始状态、退本金及S、移除席位或取消房间；与开始互斥。
- 异常：先暂停；退款／补偿执行已批准方案及唯一业务键，不调用普通取消接口全额返还。

必须持续成立：

```text
每人初始预付本金 = 已消费本金 + 未用本金 + 已退本金
所有入池赌注 = 待分配奖池 + 已付奖池奖金 + 已退赌注
实际投注 = 完整及执行中已确认付费扣款之和（不是入桌钱包扣款）
最终成绩 = 本桌唯一已确认游戏派彩之和
钱包净变化 = -入桌扣款 + 本金退款 + 游戏派彩 + 赌注退款 + 奖池奖金 + 专属奖励
正常完成时：每人已消费本金=B×N，completedPaidSpins=N
```

分账不得重复把赢家的原押注计为退款；整份奖池已经包含它。获胜奖池与专属奖励不是游戏派彩，不能进入成绩。

## 跨库结算与幂等恢复

沿用“先持久计划、后请求大厅、再提交游戏状态”的方向，补齐好友桌上下文及预付消费。不能宣称大厅与游戏数据库有一个原子事务。

| 故障点 | 恢复方式 |
| --- | --- |
| 游戏计划尚未落库 | 不发资金请求；同局唯一键重试生成／读取唯一计划 |
| 计划已存，大厅尚未提交 | 重试原requestId和相同金额／计划摘要，禁止重新开奖 |
| 大厅已提交，响应丢失 | 同requestId返回原收据；金额或上下文不同则拒绝并告警 |
| 大厅已提交，游戏未提交帧 | 从持久计划及大厅收据提交同一帧；不得退款后重抽 |
| 游戏提交成功，完成消息未投递 | 游戏Outbox重投；大厅以局序号、帧ID、完成ID去重 |
| 最终奖池已付，客户端未收到 | 查询房间终态和原结算收据，不再分奖 |

建议唯一键：入桌 `(uid, commandId)`、付费局 `(roomId, memberId, paidSpinIndex)`、帧 `(betId, frameIndex)`、资金 `(scene, requestId)`、房间结算 `(roomId, settlementVersion)`、奖励 `(roomId, uid, ruleVersion)`。相同键不同payload必须冲突，不能当成功。

调度任务使用持久到期时间、租约、重试次数和递增fencingToken；拿到旧租约的worker不能再写新状态。房间与资金更新遵循固定锁顺序，并用 expectedVersion/CAS 防止重复开始、取消与开始并发、旧worker结算。websocket发送失败不回滚资金事务。

## API与事件草案

命令使用登录态、幂等键及必要的 expectedVersion。以下路径需后续按仓库协议生成流程定稿，本次不修改生成文件。

| 类型 | 建议接口 | 说明 |
| --- | --- | --- |
| REST | POST /api/friend-tables | 创建并一次扣款；返回扣款收据与房间快照 |
| REST | POST /api/friend-tables/join | 邀请凭证、确认规则摘要、幂等键；扣款与占席同事务 |
| REST | POST /api/friend-tables/:id/ready | 建议准备／取消准备 |
| REST | POST /api/friend-tables/:id/start | 建议房主开始；服务端重新验证 |
| REST | POST /api/friend-tables/:id/leave | 仅开局前退款退出；已开始拒绝退赛并返回继续状态 |
| REST | GET /api/friend-tables/:id | 有权成员的一致快照、资金状态及baseSeq |
| REST | GET /api/friend-tables | 本人的桌记录，游标分页 |
| REST | POST /api/friend-tables/ws-ticket | 短期、单用途票据；避免把长期sid写进URL和日志 |
| REST | GET /api/user/report?scene=friend_table | 报表建议扩展；缺省保持旧客户端语义 |
| 内部 | 好友桌局执行／结算协议 | 服务间鉴权，校验房间绑定及可信场景，拒绝公网调用 |
| WS | subscribe(roomId,lastSeq) | 成员授权、缺口补发、过期全快照 |

```json
{
  "type": "paid_spin.completed",
  "eventId": "unique-event-id",
  "roomId": "room-id",
  "seq": 128,
  "roomVersion": 24,
  "schemaVersion": 1,
  "data": {"memberId": "member-id", "paidSpinIndex": 7, "payoutMinor": 1200, "totalPayoutMinor": 8600}
}
```

事件包括 member.joined/ready/left、room.started/paused/resumed、spin.frame.visible、paid_spin.completed、room.settled/canceled。事件遵循至少一次交付，客户端按seq去重；缺号拉取补发。同步快照与订阅交接必须无丢失窗口，必要时缓存baseSeq后的事件。成绩可来自逐帧增量或完成局汇总，但同一投影只能选择一种累计来源，不能两边相加。

游戏运行节奏由服务器控制并限制并发；是否逐轮同步等候所有人的完整付费链结束属于D07。建议以轮为单位推进，免费链长时显示“好友免费游戏进行中”，不截断游戏；离线也正常推进。如果产品选择保留在线手动 Spin，按钮只请求推进当前允许的同一局；服务端到达截止时间自动补位，两条路径共用同一个局序号和资金幂等键。在线是否保留此按钮属于 D07，本稿原型展示全程自动方案。

## 普通活动隔离、提现与报表

隔离必须发生在可信服务端的入账和事件生成处，不能只在页面隐藏。所有好友桌事实带场景；普通活动读模型采用明确允许的场景集合，旧记录回填或默认普通场景要兼容旧查询。

重点审计 `game_model.go`、`activity_model.go`、`loss_return_model.go`、VIP、佣金／邀请任务、签到／新手条件与统计SQL；普通亏损读取实际投注和派彩，单设 validBet=0 无效。好友桌独立来源不得加入普通赠币选项集合。未来专属奖励仍带好友桌场景，不能反向触发普通活动。

提现触发器当前按正向credit来源处理，未知来源可能拒绝入账，普通投注事件还可能抵扣流水要求。因此新增来源之前必须制定每类本金退回、原押注退回、游戏派彩、奖池所得、专属奖励的提现规则。D04未确认时禁止真实资金灰度；不能通过临时关闭全局触发器或使用普通来源绕过。

好友桌报表按已发生的消费／入账事实与时间聚合，入桌预扣不是投注，未用本金退回不是利润。采用可重放独立读模型并与账本核对；报表若异步需显示更新时间。玩法成绩按全桌累计，报表按所选日期，跨日两者允许不同但必须解释。

## 专属奖励扩展

持久化人数、B/N、每局派奖、每人总派彩、中奖局数、完整完成标记、参与关系等事实。奖励引擎只消费最终可信事实，不读客户端动画或临时榜。规则版本开桌固定，默认关闭；后续明确精度、中奖定义、限次、同伴重复、预算和反刷后才启用。奖励失败独立重试，不重复分配奖池，不修改RNG和成绩。

## 安全、运行与上线

服务端重新验证成员、实际Bet、余额、房间状态；邀请码不可枚举并限制尝试频率。对手只能获得已公开帧和必要资料，不接触对方钱包、token或未来结果。服务间使用现有鉴权基础加严格上下文校验；客户端提交的uid、score或scene均不作为依据。

观察指标至少包括待执行任务最老年龄、暂停桌数、未归零本金／奖池、跨库未完成结算、重复键冲突、报表差额、事件积压、WS缺号及重连恢复时间。持久对账任务按房间核验不变量，发现差异暂停该桌并告警，禁止自动改余额抹平。

发布采用feature flag按用户／游戏开放。停止新桌不能停止已扣款桌；部署、游戏维护和回滚需保留旧版本runner及结算能力直到存量桌清空。配置关闭游戏时，新桌拒绝，已开始桌应继续或明确暂停恢复，不能因普通游戏开关被遗弃。
