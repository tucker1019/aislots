# 好友桌：实施与验收计划

状态：设计草案，尚未开发。参见 [需求](requirements.md)、[技术方案](technical-design.md)。此处是实施顺序，不是工期承诺。

## 分阶段交付

| 阶段 | 交付与依赖 | 验收门槛 |
| --- | --- | --- |
| 0 规则定稿 | 确认人数／开始方式、提现流水、平局、故障补偿、首款游戏及节奏；审计游戏持久状态 | 形成版本化规则；多人平局未定可限制先做2人验证，提现政策未定不能真钱上线 |
| 1 资金底座 | 房间状态机、一次扣款、资金分账、幂等、开始前退款、流水来源与提现规则迁移 | 独立测试库验证并发、不变量和事务回滚；不连接真实游戏和真钱用户 |
| 2 可信游戏闭环 | 一款游戏场景绑定、预付消费、游戏计划恢复、完整付费链、可信完成事实 | 同一局重复执行不重扣／重抽，免费链计数正确，普通游戏回归通过 |
| 3 持久调度与实时协议 | 租约／栅栏、服务器节奏、Outbox、WS授权／补发、暂停恢复 | 全员离线仍完成；worker重启不丢局，未到展示时点结果不泄露 |
| 4 大厅交互 | 创建、加入确认、邀请、准备、对战只读盘面、离开、结果及记录 | 小屏可用、金额清楚、请求中状态稳定；依据现有大厅规范实现 |
| 5 活动与报表隔离 | 全部普通活动排除、独立个人报表、逐桌对账、来源审计 | 每项隔离用例通过，普通活动不受影响，钱包与好友桌资金一致 |
| 6 联合演练和灰度 | 测试环境故障注入、存量桌部署演练、运维工具、限额和开关 | 所有阻断项关闭后才按白名单逐步开放 |
| 后续 专属奖励 | 独立确认条件、金额、限次与防刷，再启用版本化规则 | 不改变RNG／普通活动；重复评估只发一次，预算与审计通过 |

前端原型可以和底层开发并行，但不能以普通钱包Spin代替好友桌结算做真钱演示。首款游戏完成全链路后再逐款审计开放，不能只看画面一致就认为适配完成。

## 验收矩阵

| 领域 | 场景 | 必须得到的结果 |
| --- | --- | --- |
| 基础资金 | B10/N20/S100，两人分别派彩180/260 | 每人入桌只扣300；实际投注各200；奖池200给B；净变化A−120/B+160 |
| 两人平局 | N局总派彩完全相同 | 各退原赌注，正常派彩各自保留；不把退款计游戏派彩 |
| 多人平局 | 3–4人部分并列第一、全员同分、余数 | 与最终确认规则完全一致；未确认前该模式关闭 |
| 入桌失败 | 余额不足、席位满、非法Bet、S超过B×N、溢出 | 不扣款、不留正式席位、不生成半份分账 |
| 入桌并发 | 相同幂等键重试、不同键重复加入、两人抢最后席 | 只允许一次入桌扣款，席位不超员；payload冲突明确失败 |
| 状态并发 | 准备／取消准备与开始、退出与开始、到期与开始同时发生 | 唯一合法状态获胜；已开始不能再全退 |
| 局数计数 | 消除多帧、免费旋转、最后一付费局触发免费链 | 一条完整付费链只计1局；不额外消费B；全部派彩计入原局 |
| 游戏参数 | 修改请求金额、buy-free、改档位、伪造scene、普通会话续帧 | 服务端拒绝越权，保持固定真实B与可信场景 |
| 游戏状态 | 未完成普通局、持久累积特征、跨桌重复开局 | 不丢失普通状态、不重复消费、不通过重置获得优势 |
| 跨库故障 | 计划前、计划后、资金提交后响应丢失、帧提交前后断电 | 原计划恢复；不二次扣款、不重新开奖、不丢派彩 |
| 任务重复 | 两worker争租约、旧worker复活、完成消息乱序重复 | fencing和唯一键生效；局数与金额只增加一次 |
| 网络 | 单人离线、全员离线、WS断线、浏览器后台／关闭 | 服务端继续；重连不重新入桌，展示当前状态与已离线完成局数 |
| 事件恢复 | 重复seq、缺号、超保留窗口、快照与订阅并发 | 去重／补发／完整快照后状态一致，不泄露未来帧 |
| 故障暂停 | 游戏维护、资金差异、配置版本不可用 | 暂停并提示；不自动判输、不重新开奖；按原版本恢复 |
| 退款 | 开始前取消、部分成员退出、退款响应丢失 | 仅退适用本金和赌注一次，资金不变量成立 |
| 异常补偿 | 已消费部分局且已有派彩、无法恢复 | 走已批准策略与审核；不伪装开局前取消，不重复补偿 |
| 活动排除 | 反水、亏损返还、签到、VIP升级／保级／周月礼金 | 好友桌投注／派彩／奖池／退款／奖励都不污染普通指标 |
| 活动排除 | 代理、邀请、新手、充值／提现赠送相关条件 | 不贡献普通达标条件；资金转移不冒充充值或提现 |
| 提现流水 | 各来源credit、内部本金消费、退款和原有流水要求 | 符合D04定稿；来源触发器不报未知来源、不错误增减要求 |
| 报表 | 进行中、跨日、取消、平局、获胜、未来专属奖励 | 投注取本金消费；资金与利润分开；可追溯全桌、不重复计算自有赌注 |
| 正常业务回归 | 普通付费／免费链、钱包、原活动、原报表 | 普通场景行为与既有口径保持一致 |
| 权限 | 非成员订阅、猜邀请码、窃取过期票据、客户端伪造成绩 | 拒绝越权、限流，服务端结果为唯一依据 |
| 版本与运维 | 部署中有活跃桌、关闭入口、回滚、停用游戏 | 拒绝新桌但持续完成存量；不遗留扣款桌 |
| 奖励扩展 | 默认关闭、重复完成、重复规则评估 | 初版不发奖；未来开启后同规则版本最多发一次 |

自动化优先验证资金不变量、跨库幂等、状态并发和活动隔离；交互用端到端验证确认金额、网络重试和离开恢复。所有破坏性故障注入仅在隔离测试数据与测试服务执行。

## 灰度与运维准备

1. 测试环境使用独立测试账户与虚拟资金，验证2人完整闭环及多人规则案例。
2. 上线前准备只读逐桌审计：入桌、已消费／未用本金、游戏派彩、奖池、退款、每步幂等收据和待处理游戏计划。
3. 运维动作限定为暂停、重试同计划、恢复和经授权补偿；每次记录操作者、原因、版本和资金收据。禁止直接编辑成绩／余额。
4. 首次灰度按用户白名单、单款游戏、资金／局数／并发上限开放；限额数值需要业务确认，不在本文臆定。
5. 观察任务积压、未归零资金、活动隔离差异、对账差额和断线恢复。资金差额立即停止新桌并暂停受影响桌。
6. 回滚先关闭创建／加入，保留已有版本的worker、游戏计划恢复和结算，待存量资金归零后再卸载模块。数据库新增结构先保留，不做破坏性回滚。

## 开发启动前检查点

- D01–D08逐项标记确认、延期或限制范围；延期项不能悄悄使用建议默认值。
- D04提现流水、实际Bet计算、首款游戏状态隔离必须先形成可执行规则。
- D05未完成前不能开放自动异常补偿；真钱运行前须具备异常处理与审核路径。
- 协议、账本来源与数据库迁移先评审，再按仓库规范生成和实现。
- 交互原型只用于评审；业务验收以实际可信资金事实及服务端状态为准。
