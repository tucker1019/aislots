# 本地统计入库索引优化

范围：只改本地及迁移源码，不连接或修改公网测试环境。

1. 给已确认结算按 uid/game_id/bet_id 汇总的查询新增部分覆盖索引，包含 debit、credit、created_at，保持原结算校验与统计语义。
2. 用隔离 schema 的集成测试验证索引存在、查询自然使用索引，且借贷汇总不串用户/游戏、不包含拒绝记录。
3. 本地现有表用 EXPLAIN ANALYZE/BUFFERS 做索引前后对比，再采样统计队列变化；本地无足够积压时用隔离数据库基准测量入库能力，明确不能代替小规格测试机验收。
4. 将索引登记为幂等迁移。已有大表本地先独立执行 CREATE INDEX CONCURRENTLY，再检查有效性；正常启动迁移仅兜底，不重建已存在索引。
5. 跑相关及完整 Go 测试、lint，记录本地耗时、扫描块数、处理/新增速率及验证边界。

## 本地实测（2026-11-12）

- 本地现有表约 217.5 万条记录，同一真实订单查询执行 7 次取中位数。
- 建索引前：Seq Scan，93.328ms，56,502 个 shared blocks；建索引后：Index Only Scan，0.033ms，5 个 shared blocks。约 2,828 倍仅指这条查询，不能代表完整链路同比提升。
- 本地使用独立 CREATE INDEX CONCURRENTLY 创建，有效性检查通过；耗时 20.893 秒，索引约 178.7MiB，未重启服务、未修改测试环境。
- 包含实际 CompleteGame 排行榜和连胜更新的串行基准：200 次，16.526ms/次，60.51 events/s；Apple M1，本地隔离 schema，2 万条背景结算。没有 HTTP 和消费轮询开销，表规模也不同于现有真实表。
- 建索引前 30.01 秒实际队列：新增 7、处理 8，积压 3→2；建索引后 30.01 秒：新增 7、处理 7，积压 0→0。本地需求约 0.233/s，基准处理能力超过本地新增速度，但实际样本没有持续积压，不能用于推算测试机清空时间。
- 结论：本地索引已消除该全表扫描，低负载队列已处理完；测试环境能否稳定超过新增速度，仍需在测试机应用索引后用有积压的连续窗口测量，本次未操作测试机。
